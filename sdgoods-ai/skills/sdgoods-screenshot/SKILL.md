# SDGOODS 串口截屏

## 何时使用
- 验证 UI 改动、字体排版、画面是否正确（尤其手指够不到的启动台/菜单界面）。
- 单张约 2~5 秒（JPEG 编码）或约 25 秒（旧固件回退 RGB565）；比烧板子试错便宜得多。

## 🔴 截屏的**证明力边界**（2026-09-29 定案，先读这条再下结论）
截屏走的是 `lv_snapshot_take_to_buf` —— **读的是 LVGL 的帧缓冲，不是面板回读**。
所以：
- ✅ 能证明：LVGL 的对象树、布局、字体、配色对；
- ❌ **不能证明**：面板真的在显示这张图。
  「截图完全正常，但用户说屏幕上什么都看不到」是**真实且常见**的组合，
  此时问题在**显示链路**（背光 / 内部 DMA 弹跳 / 面板寄存器），不在 UI。
  ⇒ 别拿「截图正常」去否定「看不到画面」的报障。定位方法见
  skill `sdgoods-crash-triage` §5c（整屏 flush 拿不到内部 DMA）。
- ⚠️ 同理：截图也**证明不了**「帧在持续刷新」。要证刷新，看串口的 flush 失败行
  （`draw_bitmap FAILED` / `internal DMA largest_free=`），不是看图。

## ⚠️ 最常见的失败：忘了加 `-t`

`screenshot_recv.py` **默认只是「监听等设备发图」**，不会自己发 `'s'`。
⚠️ 脚本位置：在**谷仓工程仓库内**（如 `SDGOODS-ESP32S3/tools/screenshot_recv.py`、派生工程 `<APP>/tools/screenshot_recv.py`），**不在本 skill 目录**（skill 只封装文档）。
不加 `-t`（或 `--pre`）就跑 ⇒ 老老实实等满 120 秒然后
`等待超时：120 秒内没有收到完整截屏` —— 很容易被误判成「设备没在跑 / 截屏链路坏了」，
其实设备好好地在跑。要主动触发**必须**带 `-t`：

```bash
python3 tools/screenshot_recv.py -p /dev/cu.usbmodemXXXXXX -t -o shot.jpg
```
（超时第一排查顺序：① 有没有 `-t` ② 设备是否在跑应用，再去看链路。）

## 运行（从仓库根目录）
> ⚠️ **脚本只在 `SDGOODS-ESP32S3/tools/` 里有一份**。它跟被截的是哪个固件**无关** ——
> 不管当前板子上跑的是什么，一律 `cd <仓库根>` 再跑。别去 skill 目录下找 `tools/`（那里只有 SKILL.md）。

```bash
# 自动向串口发 's' 触发并接收 1 张，存 shot_时间戳.png
python3 tools/screenshot_recv.py -t

# 指定端口 / 连续抓 3 张 / 指定输出
python3 tools/screenshot_recv.py -p /dev/cu.usbmodemXXXXXX -n 3 -o my_shot.png

# 探测固件能力（串口发 '?'，看是否含 SHOT）
python3 tools/screenshot_recv.py --caps

# 不需要设备，自检解析 + PNG 写出
python3 tools/screenshot_recv.py --selftest
```
- 协议：`===SHOT-BEGIN w=360 h=360 ...===` 文本头 + 定长原始二进制 + `===SHOT-END===`；
  `fmt=1` 为 JPEG（PC 直接落 .jpg），`fmt=0`/无字段为 RGB565（PC 转 PNG）。
- 需要 pyserial：用带 pyserial 的解释器（系统 python3 可能无）。脚本会提示可用路径。

## AI 处理策略
- 接收前**先让用户关掉** `idf.py monitor` / 串口助手 / 浏览器 Web Serial 页面——
  它们占住同一串口会导致打不开或数据串台。
- ⚠️ **幻触**：串口一打开，屏上就可能凭空出现点/划，曾多次被误判成固件 bug。典型表现：
  ① 凭空拉出控制中心（截回来的是 CC 而不是主页）；② 横向拖动主页图标行（像「被滑过一格」）；
  ③ 幻触点按触发 `launch slot N` 把设备切进某个 app。
  对策：打开串口后立刻 `ser.rts = ser.dtr = False`，**能减轻但不能根除**
  ⇒ 判图前先确认「这一屏是不是我要的那一屏」。
  （注：USB-Serial-JTAG 的 DTR/RTS 并**不**接到 CHIP_PU，所以这两种电平都不会复位芯片——
   仓库里的 `tools/screenshot_recv.py` 反而把两者置 `True` 且工作正常。别把幻触归因成
   「电平设错导致复位」。真要复位芯片用 **DTR 脉冲**：`setDTR(False); sleep(0.05);
   setDTR(True); sleep(0.1); setDTR(False)`；**RTS 脉冲不复位**。）
- 若被幻触切进了某个 app，写回空白 otadata 即可回启动器：
  `esptool --chip esp32s3 -p <port> write_flash 0x310000 build_xxx/ota_data_initial.bin`
- 把生成的 PNG 用 Read 工具打开「看一眼」，核对布局/文字/颜色；发现方框即字体缺字（见 `sdgoods-fonts`）。
- 真机不在手边：用 `--selftest` 验证解析管线本身无问题，再请用户上机补真实截屏。

## 把 UI 差异「量化」出来，别只靠肉眼（2026-09-21 补）

截回来一张图、肉眼看一眼就下结论，很容易翻车（360² 的小图 + JPEG 压缩 + 抗锯齿，
「少了一条 4px 的灰条」「图标偏了 2px」这类根本看不出来；也容易把封面图**自身**的灰内容
看成 UI 缺陷）。可靠做法是把画面当数组，先问一个**能用数字回答的问题**：

```python
import numpy as np
from PIL import Image
a = np.asarray(Image.open(shot).convert('RGB'), dtype=np.int16)
r,g,b = a[:,:,0],a[:,:,1],a[:,:,2]
gray = (np.abs(r-g)<=14)&(np.abs(g-b)<=14)&(r>=45)&(r<=220)   # 阈值按主题微调
# 例：找「细长条」= 最长连续灰 run（竖条按列扫、横条按行扫），修前修后对比数值
```

可复用的三招：
1. **找细长条 / 边框 / 滚动条**：按行/列扫最长连续 run。修前 49px → 修后 10px 就是「条没」，比肉眼可靠。
2. **判断「位置有没有变」**：在被改对象的**内部区域**（避开外圈，外圈颜色可能是随机的）做 ±6px 平移互相关，
   最佳对齐若在 `dx=dy=0` 且平均差 < 1 灰度级 ⇒ 位置没动。
3. **连通域 + 形态过滤**：`n≥40` 的连通域里挑 `(w≥3 且 h≥40)` 或 `(h≤4 且 w≥40)` 的，就是条状物。

⚠️ 反面教训：**先确认「这个像素属于 UI 还是属于内容」**。封面图是 AI 生成的像素画，
本身就带灰色描边/文字 ⇒ 灰像素扫描一定会命中它们。所以定位时必须结合
「哪些图标有、哪些没有」做**对照**（这次就是靠「只有贴了封面的图标有灰条、字母回退态没有」锁定根因的）。

### 量化判据本身要先用「几何反推」自检一次（2026-09-27 血泪）

**症状**：固件没问题，判据把**容差问题**报成 🔴，于是白折腾一轮（一晚连踩 4 次）。

**铁律**：写完判据后，先拿**设计常量**反推一遍「屏幕上应该看到什么」，再跟脚本口径对齐。
对不上就是脚本错，不是固件错。**别急着去改固件。**

四个实例（都发生在首页顶部状态条核验里）：

| 假 🔴 | 真相 |
|---|---|
| 凸点量到 4×7，判据要 4×9 | 凸点带 `radius=2` 圆角 + JPEG 弱化最外 1px ⇒ 可见核心只有 4×7。判据改「4 宽、7~9 高」。 |
| 「solo 时徽标区域为空」失败 | 检测区写成 `x128..170`，而 solo 的电池框左沿**正好 155** 落进区内 ⇒ 量到的是框自己。solo 专用区右界必须 <155。 |
| 徽标量到 16×13，判据要 24×17 | 24×17 是**容器**尺寸；图形（底点+三弧）居中于容器只占 16×13。反推：最外弧 r=11、弧心在容器 (12,12) ⇒ 屏幕 x 143.6..160.4，与实测 144..159 吻合 ⇒ 渲染正确。 |
| 开关滑块量到 73 宽 | OFF 态滑块色 `#8E8E93` 与「OFF」**文字同色**，bbox 把两者合并了。 |

### 多行堆叠版面：量「墨迹带节距」，别信算式自洽（2026-10-02 血泪）

**症状**：往主页时钟块（时间 / 日期）下面加第三行（下载速度），位置算式完全自洽、
也没压到上一行 —— 但真机截屏一看，第三行**肉眼偏挤**。

**根因**：`DLSPD_Y` 写成「上一行**盒底** + 2」。这是**"盒子不重叠"的下限**，
不是**"视觉等距"的位置** —— 两者在这张脸上差 **4px**。
量出来是节距 **22 / 18**（4px 落在 10px 高的字上 = 40%，所以肉眼能看出来）。
改成与上一档同节距（`CLOCK_Y + 2×(CLOCK_LH + CLOCK_LINE_GAP)`）⇒ **22 / 22**。

**通用判据**（凡「同宽盒子 + 居中」堆叠的多行文本都适用）：
1. **纵向**：逐行量墨迹带的 y 起点，**相邻几档的间距必须相等**（不是"没重叠"就行）；
2. **横向**：各行的墨迹**中心**应当一致（偏差 ≤1px —— 中英混排宽度不同，比左沿靠不住）；
3. **反例对照**：要有一张「没有这一行」的图，证明那条带确实不在（否则判据恒真）。

🔴 **纵向节距一律按「墨迹带中点」算，不要按「带顶」算**（2026-10-02 补，血泪）：
带顶是 x-height/capital 的上沿，抗锯齿把它糊出去 1px ⇒ **阈值一变、结论就变**。
实测同一批图：带顶算 `22.0/22.0`（thr150）vs `21.0/22.0`（thr100），
凭空多出 1px 的"行距坏了"；**中点算 22.0/22.0 vs 21.5/22.0**（差 0.5px = 半像素量化）。
带底（基线）也稳，但遇到带下伸部的字会整段变长 ⇒ 中点最通用。
判据写成「**相邻节距之差 ≤1px**」，别写成「必须等于 22」——后者是在赌阈值不变。

**现成工具**：`SDGOODS_LAUNCHER/tools/measure_clock_rows.py`（量 y 带 / x 范围 / 中心 / 节距）。
它固化了三个**不能随手改**的口径（2026-10-02 更新，旧版本写的是 thr=150 / x1=120）：
- **`thr=100`**：时钟块现在有**两种墨色** —— 时间/日期近白（≈226）、下载速度是
  `COLOR_GRAY` 灰（0x8E8E93 ≈ **143**）。阈值要落在灰字与背景本底之间。**改了 UI 颜色
  就要回头复核这一条**，否则灰字直接漏检、报「这行没上屏」（这个假阴性本轮真踩过）。
- **窗口 `x1=110`（不是圆环左沿 43）**：`x1` 取 120 时，**主页图标圆环的左弧
  （落在 x≥117，实测最亮 115）会从右缘漏进窗口** —— 白字阈值 150 时被挡住看不见，
  阈值一降到灰字能用的档位它就变成**一条假的行**。收到 110 是"离弧线还有 7px"的一刀切。
- 窗口 y 只覆盖时钟块，避免把状态条 / 下面的图标算进来。

⚠️ 配套那条老坑：**只改常量 ⇒ `.bin` 大小可能一字不变**（本次两版都是 `0x1a95a0`）⇒
判「新码在不在跑」要看**真机可见位移**（这次是 +4px）或版本串，**不能看体积**。

### 要验「下载时才出现的 UI」⇒ 同会话里造态 + 抓日志 + 截屏（2026-10-02）

有些 UI 只在一件事**正在发生**时才有内容（下载速度、进度环、对账态）。
只发 `'s'` 截一张是等不到它的 —— 要么拍到空窗（首包还没到），要么拍完早没了。

**做法**：一个脚本里按时刻表串起来，**全程独占串口**：
```
t=0.5s  {bwurl:<地址>!      # 可选：把下载地址改成自己能控制的（绕过 15 分钟过期的预签名直链）
t=2.0s  {bw<KB>!            # 驱动下载链路（或 '+' → '*' 走真实安装链路）
t=Xs    's'                 # 下载进行中截屏 ← 这一张才是判据
```
- 同时把串口原始流落盘，从里面 grep 数据源日志（本次 `launcher_ui: dl speed: 93 KB/s`），
  **截图里的数字必须与日志逐字对上** —— 这才叫"图上那个数是它算的"。
- 想验真实链路就用 `'+'`（开第 1 条推送项安装）→ `'*'`（选第一槽 → 开始下载），
  这是**唯一**能同时看到「进度环 + 速度行」的路径；纯测速键不画进度环。
- ⚠️ 注入串里**不能出现 `s`/`S`/`?`/`X`/`R`**（BSP 控制台提前消费），
  所以 URL 要挑**不含字母 s** 的（`http://10.0.0.1:8099/t.bin` 这种）。
- ⚠️ 预签名直链**约 15 分钟过期** ⇒ 拿旧地址测速会得到 `status=403 recv=0`、
  速度恒 0、那一行当然不显示 —— 别把这当成「功能没实现」。
- 参考实现：`/tmp/dl_speed_ui.py`（测速驱动）与 `/tmp/real_install_shot.py`（真实安装驱动），
  都复用 `screenshot_recv.py` 的 `ShotAssembler` 解析分帧。

**🔴 采集时长要按「真实链路速度」估，不能按局域网估**（2026-10-02 复测教训）：
同一条 2 MB 安装包，局域网明文 ~300 KB/s ⇒ 7 s 下完；公网 HTTPS 只有 15 KB/s ⇒ **229 s**。
按局域网估的 40 s 采集脚本会"跑完却没看到 `install ok`"，**极易误判成下载卡死**。
⇒ 先跑一次拿实测速率，再定 `-t`；宁可给到 2.5 倍余量。

**🔴 判「这一帧是不是下载中」要先看日志的时刻，再定截屏秒数**：
别拍脑袋写 `--shot-at 9.0`。先从日志里拿 `push_ui: dl slot=N xx% (a/b)` 与
`launcher_ui: dl speed:` 的时间戳，确认那一刻确实在收数据，再反推 t。
否则很容易拍到**首包之前的空窗**（本次 `①0%` 那帧）。不过那种空窗别浪费 ——
它正好是「**首包未到时不显示 `0 KB/s`**」这条判据的反例证据。

**五态验收矩阵**（凡"随事件出现/消失"的 UI 都按这个矩阵走，缺一不可）：

| 态 | 造法 | 判据 |
|---|---|---|
| 静止 | 什么都不做 | 该行**不存在**（反例） |
| 事件进行中 | `{bw<KB>!` 或 `+`/`*` | 出现，且与数据源日志逐字一致 |
| 事件**刚起·首包未到** | 截在 `starting download` 之后、首个 `dl speed:` 之前 | **不得**出现占位值（`0 KB/s`） |
| 事件结束 | 等 `install ok` | 整行**消失** |
| 重启后复测 | 硬复位后再走一遍「进行中」 | 仍出现（证明控件/定时器在主页重建时被重新创建，不是只在首启有效） |

### 颜色撞色 / 相邻部件混入 ⇒ 用 8-连通域，别用整块 bbox（2026-09-27 补）

`bbox_of(区域, 颜色)` 在下面三种情形**必然**报错 —— 改用**连通域**：

- 同色部件相邻（灰开关 `#3A3A3C` vs 灰 Scan 按钮；滑块的 `#8E8E93` vs OFF 文字）；
- 目标部件贴着另一个同色部件（电池框左沿与徽标检测区重叠）；
- 区域把背景/遮罩的近似色一并框入（弹窗面板 `#1C1C1E` vs 遮罩 ⇒ 容差要从 14 收到 10）。

现成实现（可直接抄）：

```python
def components(im, region, target, tol, min_area=6):
    """8-连通域分离：返回 [(x0,y0,x1,y1,area)]，按面积降序。"""
    x0, y0, x1, y1 = region
    W, H = x1 - x0, y1 - y0
    mask = bytearray(W * H)
    for yy in range(H):
        for xx in range(W):
            if near(px(im, x0 + xx, y0 + yy), target, tol):
                mask[yy * W + xx] = 1
    seen = bytearray(W * H)
    out = []
    for idx in range(W * H):
        if mask[idx] and not seen[idx]:
            stack = [idx]; seen[idx] = 1
            xs, ys = [], []
            while stack:
                i = stack.pop(); cy, cx = divmod(i, W)
                xs.append(x0 + cx); ys.append(y0 + cy)
                for dy in (-1, 0, 1):
                    for dx in (-1, 0, 1):
                        nx, ny = cx + dx, cy + dy
                        if 0 <= nx < W and 0 <= ny < H:
                            j = ny * W + nx
                            if mask[j] and not seen[j]:
                                seen[j] = 1; stack.append(j)
            if len(xs) >= min_area:
                out.append((min(xs), min(ys), max(xs), max(ys), len(xs)))
    out.sort(key=lambda b: -b[4])
    return out
```

用法：先按**面积降序**取最大域（主体），再按特征挑次域 —— 例：凸点 =「高 ≥6 的次大域」，
滑块 =「宽高差 ≤3 且宽 ≥18 的圆」。

⚠️ 容差要卡在「同色部件能分开、JPEG 抖动又不丢」的窗口：本次电池框用 `tol=22`
（1px 缝的过渡像素 `|0x70-0xE0|=112` 一定不匹配；放到 `tol=30` 就开始有合并风险）。

### 🔴 判色判「色相族」，别判全等；找边界禁单点/单列（2026-09-28 双踩）

**① 截图是 JPEG ⇒ 色度子采样（4:2:0）会把细笔画的红/白拉淡，全等判据必假阴性。**
实测同一张图：DEL 红字核心只量到 `(160,60,57)`（理论 `(255,69,58)`，**仅 ~58% 覆盖**）、
空格白字 `(187,189,186)`（不是 255）⇒ 三条「红字/白字」判据全部报 🔴，但代码明明生效了。
**判它是采样问题而非 bug 的旁证**：同一帧里主题绿量到 `(164,224,4)` ≈ 理论 `(161,227,7)`
—— **绿能全等、红不能**，正因为红通道（和亮度）被子采样拉低。
⇒ 判色改用**色相族**（宽松但依然排他）：

```python
def is_red(c):   # c = (r,g,b) 核心像素
    return c is not None and c[0] > 120 and c[0] - max(c[1], c[2]) > 60 and abs(c[1] - c[2]) < 25
def is_white(c):
    return c is not None and c.min() > 150 and (c.max() - c.min()) < 14
```
（配合上面「取差异最大的前 25% 像素」拿核心，两者一起用。）

**② 找控件边界（输入框/面板/键盒）禁用单点或单列采样。**
`vseg(a, col=180, ...)` 这类「取屏幕中线那一列、扫最长的 ≈框底色 run」的写法，在
**文字正好穿过该列**时会量出荒谬结果：字的抗锯齿边缘像素也是暗灰、落进「≈框底色」容差里，
于是把框上沿认到字的顶上 —— 本次实测把输入框量成 `y=(48,104)`（真值 `(75,104)`），
**误判「输入框没上移」**，白查一轮。
⇒ 改成**按行走访 + 只认「整行匹配像素数 > 阈值」**：框体那几十行每行有 ~200 个匹配像素，
文字行只有零星几个，一眼可分：

```python
def vseg(a, col_lo, col_hi, y1, y2, box, tol=14, need=120):
    rows = a[y1:y2+1, col_lo:col_hi]
    hit = (np.abs(rows - box).sum(axis=2) < tol * 3).sum(axis=1)
    ys = np.nonzero(hit > need)[0]
    return (y1 + int(ys.min()), y1 + int(ys.max())) if len(ys) else None
```

这两个坑都是**「判据报错 ≠ 固件错」**的又一例（同上面「几何反推自检」那条铁律）：
先怀疑采样口径，再动固件。

**③ 判「某个控件的底色」时，必须从源码宏取真值，别拿另一个控件的颜色凑容差。**
（2026-09-28 第二次踩，仍是同一条 `vseg` 判据。）
`vseg()` 里的 `box` 是**被测量控件自己的底色**。本次要量**键盘页输入框**（真值
`(26,31,35)`），却沿用了**键**的底色 `#2C2C2E = (44,44,46)` 再放宽容差到 `±42`：因为两个色
相差 `|26-44|+|31-44|+|35-46| = 60 > 42` 本该不匹配，结果**只有键区那 112 行**能过阈值
⇒ `y` 恒为 `None`，判据报「输入框不见了」。
更糟的是这坑**会先假通过一次**：更早一版用 `(58,47,47)±42` 时「差 60 也能蹭到别的像素」，
碰巧量出了对的 `x` 跨度 ⇒ 让人以为这条判据是可信的。
⇒ **规矩：`box` 一律先去源码里抄**（如 `KB_FIELD_*` / `KEY_BG` / `CC_COLOR_*`），
容差收到 `±9` 级别；**期望值也一样**（本次把 `KB_FIELD_H` 凭印象写成 30，真值 **40**）。

**④ 数「同类控件的个数」不能扫控件中线那一行 —— 会被控件里的文字切成好几段。**
本次要验「键盘行 0 仍是 11 颗键」，扫键心 `y=156` 那一行的键底色连续段 ⇒ 得到 **35 段**
（标签文字把每颗键切成 2~3 段），过长的只有 9 段 ⇒ 误判「键数变了」。
⇒ 改扫**控件上沿那几行**（`y 142..147`，无文字）并按**列覆盖率**（`≥80%` 的行数是键底色）
连通成段 ⇒ 稳定得到 **11** 颗、各宽 17..20（`KB_W=25` 减去圆角与抗锯齿）：

```python
col = (np.abs(a[142:147, :] - KEYB).sum(axis=2) < 27).sum(axis=0)   # 5 行覆盖
on  = col >= 4
```
⚠️ 行数一变阈值就得跟着变（6 行配 `>=5` 会多切出两个小段 ⇒ 又数成 9 颗）；
**先跑一遍探针把「段宽清单」打出来**再定阈值，别直接写死。

### 定位第一步：先把圆心**量**出来，别估（2026-09-21 连踩三次）

要给某个圆形 UI 元素做半径/角度分析，第一件事是拿到它的圆心。这一步估错，
后面所有数字全是垃圾，而且**错得看不出来**（会输出一堆自洽的荒谬值）。三种典型的错法：

1. **肉眼看截图估圆心** —— 360² 的小图在脑子里换算成坐标，我目测出 y=228，
   实测是 **y=180**，差了 48px。一眼扫出来的绝对值不可信。
2. **把掩码切在 `x >= w/2`** —— 主页第 1 个图标圆心**正好在 x=180**（屏宽一半），
   这一刀等于只留半张圆盘，质心被拉到 x=155。判据要写成「只在某个 ROI 内」，
   不是「只取左半边」。
3. **用宽亮度窗抓「灰色」** —— `lum in [70,160]` 会把标题/电量的**抗锯齿灰边**
   一起吃进来，把质心拉出圆盘外。灰底回退态的圆盘是很均匀的一个值（实测 lum≈110），
   窗口收到 ±10 就够，噪声全排除。

**最稳的顺序（照抄即可）**：
```python
# ① 先把掩码打成缩略 ASCII 图，肉眼确认形状与包围盒 —— 这一步比任何自动定位都快
for by in range(0, 360, 6):
    print(''.join('█' if m[by:by+6, bx:bx+6].mean() > .9 else
                  ('#' if m[by:by+6, bx:bx+6].mean() > .6 else
                  ('◇' if m[by:by+6, bx:bx+6].mean() > .3 else ' '))
                  for bx in range(0, 360, 6)))
# ② 从 ASCII 图读出包围盒，在该 ROI 内取「均匀灰」像素求质心（别切半边）
# ③ 用「外缘半径 ≈ 60」自证：偏离就说明 ROI 里混进了别的东西
```
**主页图标行的已知几何**（可直接拿来当基准，省掉第 ①② 步）：
圆盘直径 120（`ICON`）、间距 22（`GAP`）、第 i 个圆心 x = `180 + i*142`（i=0 时 x=180），
**行圆心 y = 180**（屏幕正中）；弧光半径 ≈ 48（`hl_size = ICON*84/100 = 100`，弧从 r=50 向内 4px）。

**带封面的图标不能用来量弧光**：封面是像素画，本身就有亮/灰像素，会把半径剖面和角度直方图
全糊掉。要量圆盘上的装饰（弧光、描边），先把该槽的封面块**备份后擦掉**进回退态
（`read_flash <槽尾地址> 0xC000` → `erase_region` 同区间 → 量完 `write_flash` 写回）：
回退态下圆盘是纯灰 + 两个白字母，信号干净。**擦之前一定先备份**。

**「端点圆帽 vs 平切」这类 3~4px 的差异，量化窗口不能开太大**：弧宽 4px、半径 50px 时，
圆帽只往端点外多涂约 2px（≈2.3°）。用「端点 ±3° 内亮像素占比」这种窗口，
一半窗口落在弧外 ⇒ 真正的平切也会显示约 50%，看起来像「有圆帽」。
更干净的判据是**看端点角度之外有没有亮像素**，以及**同角度下端点区 vs 弧中段的占比之比**。
结论：这种量级的差异本来就接近视觉阈值，别用数字去"证明"用户没看见的东西，
要如实说明「这一项只值 2px，主要观感变化来自别处」。

### 🔴 用户给「参考图」时：形状照抄，**尺寸必须按最终渲染像素重定**（2026-09-29 踩）

用户丢一张参考图让你改图标/控件时，**别把它当 1:1 的比例尺**。参考图通常是在比真机大好几倍的
画面上截出来的：本次参考图是 **103px** 圆盘，实机图标只有 **27px** 圆盘（差 4 倍）。
严格照抄比例做出来的细节，渲染后**只有 3×4 像素**，糊成一粒、完全读不出形状。

定式四步：

1. **先把参考图量化，别目测**：取前景掩码 → 包围盒 → 逐行 span（或连通域），量出每个特征的
   尺寸 / 角度 / 间隙。这一步能顺带**纠正肉眼判断** —— 本次就是靠它发现「挂片轴向**垂直于**
   该处半径（＝沿圆的切线躺）」，靠肉眼只会画成沿半径往外戳。
   判据可复用：径向单位向量与特征轴向的**点积 ≈ 0** ⇒ 该特征是「切线方向」的。
2. 换算缩放系数 = 目标尺寸 / 参考图同项尺寸，逐项落位。
3. **再把「渲染后 < 4px」的特征单独放大**（目标 ≥3px），否则干脆不画。
   ⚠️ 间隙/缝隙也要按**屏幕像素**给（本次给 3px）：照抄比例会得到 0.5px，一糊就粘上。
   ⚠️ 顺便重定「居中」：特征是偏在一侧时，要按**整体包围盒**配平，而不是让主体居中
   （本次圆盘圆心从画布中心左移 2.5px，整体才居中）。
4. **验收：缩放到同一基准再比。** 把参考图裁到包围盒、缩放到「主体直径与实机一致」，
   再与实机裁切并排（三格：参考图 / 各版实机 / 定稿）。
   直接拿参考图原尺寸和实机小图并排，只会得出「实机的特征好小」这种无用结论。

⚠️ 通用纪律（所有对照图都适用）：拼图前**先归一化基准**（圆盘直径 / 控件宽度 / 字号），
否则读者会把「大小差异」当成「形状差异」。本次归档见
`SDGOODS_LAUNCHER/tools/verify_shots/devpage/icon_dev_compare.png`。

## 🔴 串口字节级协议：有 5 个字节**永远到不了**应用层（2026-09-28 踩，症状极误导）

`components/sdgoods_console.c` 的 `console_rx_task` 在把字节交给
`sdgoods_console_ext_cmd()` **之前**，自己先消费掉 **`?`、`s`、`S`、`X`、`R`** 五个字节
（分别＝查能力 / 截屏 / 截屏 / 二进制注入 / 重启）。剩下的才按 `b >= 32 && b < 127`
转给应用层。⇒ 你挂在 `ext_cmd` 里的任何「多字符输入」协议，**遇到这 5 个字符会静默少一个字符**。

真实案例：给设备注入身份令牌（`sdg_dev_<hex>`，**首字符恰好是 `s`**）时，
- 症状①：令牌少一个字符 ⇒ 服务端哈希对不上 ⇒ 报 **401「设备令牌无效或已吊销」**
  —— 看着像平台侧问题，其实是本地串口吞了字符；
- 症状②：被吞的 `s` **顺手触发一次截屏** ⇒ 串口突然涌出 15KB JPEG + `===SHOT-END===`。
  ⚠️ 这两个症状是**同一个原因**，别拆成两个 bug 查；也**不要**据此认为「设备会自触发截屏」。

**规矩**：任何要经串口送入的**多字符值**，协议里必须自带转义（启动器用 `%XX`，
`%73`=`'s'`、`%25`=`'%'`），且**转义拼出的字节不再参与终止符判断**（这样值里真出现
`!`/`\n` 也能用 `%21`/`%0a` 送达）。单字符调试键只用标点（见下），可绕开这 5 个字节。

排查提示：这层在 BSP 里、**比应用层日志更早**，所以应用层日志里**什么都看不到**。
怀疑被吞时，直接读 `sdgoods_console.c` 那个 else-if 链，别只 grep 自己的 `ext_cmd`。

### 🔴 2026-10-02 补：`{` 是**有状态**的注入入口 —— 裸发一个 `{` 会吞掉后续**所有**单字符命令

启动器的 `ext_cmd` 用 `{` 作为「多字符注入」的开始符（`{…!`，见 `main/launcher_main.c`：
`{x,y,dx,dy,frames!` 合成手势 / `{wipe!` / `{<name><0|1|r>!` 命名开关）。
**`{` 一旦进来就只把 `s_in_mode = 3` 挂在那里等后续字符**（直到收到 `!` 才提交）——
在那之前，所有单字符调试键（`c` / `d` / `b` / `n` …）**全被吞进那个缓冲**。

真机症状（本轮踩）：想用 `{` 点一下设置页里某按钮，结果后续 `d`、`b` 命令「集体没反应」、
**截回来的几张图一模一样**；而日志里 `bsp-console: serial rx 'd'` 明明都有回显，
看着像「收到了但没执行」。

⇒ 三条规矩：
1. **用 `{` 一律带 `…!` 收尾**。要点按某坐标就用注入形态 `{x,y,0,0,4!`（`{84,169,0,0,4!`）。
2. **判「命令有没有生效」看该命令自己的日志，别只看 `serial rx` 回显** —— 回显只证明字节
   到了 console，证明不了它被当成命令执行。已经挂住时，单独发一个 `!` 把它提交/清掉。
3. `launcher_main.c` 里那种 `else if (c == '{' || c == '}' || c == '|')` 的分支，**`{` 那一支
   永远不可达**（`{` 在前面就被注入模式 `return` 掉了）⇒ 是死代码。要点按钮就换字符
   （`}` / `|` 仍在用），或直接用注入形态。

### 一次 `--cmd` 可以**串联多条** `{…!`（2026-10-02 补）

注入模式遇到 `!` 就提交并复位，所以紧接着的下一个 `{` 会重新开始 —— 一条命令串里写几条都行，
设备按顺序逐条执行：

```bash
# 先删壁纸（造「无壁纸」态），紧接着上滑（验门槛）—— 压在同一次会话里
python3 tools/shot_after.py -p /dev/cu.usbmodemXXXXXX \
    --cmd '{wallr!{180,330,0,-25,3!' --wait 1.5 -o /tmp/a.jpg --log /tmp/a.log
```

为什么必须压进同一会话：**后台任务会在几秒内把状态改回去**。实例：`{wallr!` 删掉本地壁纸后，
心跳 **~2.3s** 就发现 `wallpaper: meta differs … -> fetch` 并在 ~7s 内重新下载回来
（sha 与删除前逐字节一致）—— 分两次会话发命令，第二发就已经不是「无壁纸」态了。

### 🔴 短动画（<400 ms）**截不到中间帧** —— 别因此判「没有动画」（2026-10-02 血泪）

`s` 截屏从「PC 写完字节」到「设备真正抓帧」有 **~400 ms** 的延迟（实测：注入 0.15s 后发 `s`，
`shot: captured` 的时间戳比手势释放晚 **420ms**；把日志里这两个时间戳相减就能自己量出来）。
⇒ **任何短于 ~400ms 的动画/过渡，截图里永远只有终态**。判「淡入淡出有没有生效」时，
220ms 的动画在 0.08s / 0.15s / 0.35s 三档取样下**全部**显示为"已经切完"，
差一点就误判成"动画没生效 / 瞬间切换"。

**正确做法（临时拉长 + 三张图 + 像素级判据）**：
1. 把时长常量临时改大（例：`HOME_MIN_FADE_MS 220` → **8000**），重编重烧；
2. 在**中段**抓一帧（`--wait 4.0` ⇒ 实际抓帧约在 4.4s / 8s ≈ 55%）。8s 窗里 ±400ms 抖动可忽略；
3. 判据必须**三张图**：`全显基线` / `中段` / `全隐终态`，取同一采样盒的 **max 亮度**：
   标题盒 255.0 / **126.9** / 94.2、图标行盒 248.4 / **126.8** / 50.4 ⇒ 中段落在两端之间
   = 逐帧渲染成立；
4. **必须带对照盒**：动画不该碰的区域（例：壁纸）三张图**恒等**（141.1 / 141.1 / 141.1）
   ⇒ 证明动画的作用域是对的（只淡"内容类"对象、没碰壁纸）；
5. 取完证**把常量改回原值再烧一次**（这一步最容易忘）。

**推论（通用）**：凡是"肉眼能看出但截图只有终态"的效果（淡入淡出、位移过渡、颜色渐变），
都要走这条「临时拉长 ⇒ 中段取样 ⇒ 与两端对照」的路，**不要**用「截 N 张都长一样」当反证。

#### 位移类动画（整屏拖动）：量**移动边缘**，且**方向别判反**（2026-10-03 血泪）

整层拖动（控制中心"整屏拖下 / 拖上"，`LV_STYLE_TRANSLATE_Y`）的量化判据很直接：
**量那一层的移动边缘**，不必做相关/拟合。但有两处必踩：

1. 🔴 **方向别判反**。层坐标 0..359 平移 `t` 后占屏幕 `t..t+359`；
   当 `t = −k (k>0)` 时，屏幕**顶部 `359−k` 行**被盖住 ⇒ **下沿 = 359−k**。
   我第一版量的是"**上沿**"，得出的四帧全是 `k=0`（因为只要 `0<k<360`，上沿恒为第 0 行），
   看起来像"整层根本没动"——**是 JPEG 体积（55 KB 有内容 vs 12 KB 黑屏）与结论自相矛盾**
   才发现判反了。⇒ 判据写出来先问一句"这个量随动画单调变化吗？"
2. 🔴 **必须拿"底图基线帧"做对照**：不透明的层盖住的那部分 = 本帧黑 **且** 基线不黑。
   只判"这一行黑"会把底图自己的深色区域（例：主页图标行的大片黑圆盘）误认成层。
3. 黑层（`bg_opa=COVER` 的浮层）比"内容淡入淡出"好量得多：不需要采样盒、不需要亮度中值，
   一个行号就是全部判据。实测：拖下中 下沿 68 ⇒ k=291；到位 k=0；拖上中 k=6；拖上完毕 无面板行。
4. ⚠️ 拖动的层如果是**同级兄弟**（控制中心的 9 个页面都是 `lv_scr_act()` 的子对象，

## 「无人手」验证触摸手势：合成触摸序列

串口截屏只能看画面，**看不到手势判别走了哪条分支**（点按 / 滑动 / 误触）。人手又够不到屏幕。
解法：在固件里挂一个调试钩子，**临时替换触摸 indev 的 `read_cb`**，喂进一段「按下 → 逐帧移动 → 松开」的序列，
跑完立刻还原原回调。对 LVGL 而言与真手指**完全等价**，判别分支则从串口日志直接读出来。

启动器已内置（`main/ui_launcher.c` 的 `ui_launcher_debug_synth_touch(kind)` + `main/ui_launcher.h` 声明）：

```bash
python3 tools/screenshot_recv.py -p <port> --pre 2   # 合成「从上往下滑」
# 再看串口日志里的判别结果，例如：
#   slot 0: swipe down 50 px (dx=0) -> open control center
#   slot 1: tap (max move 0 px of 24) -> app menu (launch is now inside it)   ← 2026-09-30 起
#   （此前点按打的是 "-> launch"；用户报「左右滑动经常误触会进入应用」后改成弹菜单，
#     真正启动要再点菜单里的 Open —— 见下面那条 ⚠️）
```

### 实现位置：平台层（全设备一份），启动器只是薄包装
同一套实现在 `components/sdgoods_board/src/sdgoods_tap.c`，**全设备一份**：

```c
void sdgoods_tap_synth(int x, int y, int dx, int dy, int frames);      /* 任意任务 */
void sdgoods_tap_synth_now(int x, int y, int dx, int dy, int frames);  /* 须在 LVGL 线程 */
```
- 平台弱默认 `sdgoods_console_ext_cmd` 已把 **`'0'`..`'5'`** 接上 ⇒ **任何 app 零调试代码**
  即可验证手势：`0`=点下排按钮位(180,218)｜`1`=点中心｜`2`=下划(开控制中心)｜`3`=上划｜`4`=右划｜`5`=上划(底部起)。
- 启动器里那份是**薄包装**：只额外做「起手点固定 `(70,157)`」+「每帧前 `lv_obj_scroll_to_x(s_row, 0, LV_ANIM_OFF)` 归零」两件启动器特有的事。
- 实现要点（换任何 LVGL 项目都通用）：`lv_indev_t.driver`、`driver->read_cb`、
  `lv_indev_data_t{point,state,continue_reading}` 都是**公开字段**；`lv_indev_get_next(NULL)`
  取触摸设备；`LV_INDEV_STATE_PRESSED/RELEASED`。序列放完用帧计数器自动还原原 `read_cb`。
- ⚠️ **日志 tag 是 `gesture`，不能是 `tap`**：tag 取 `tap` 会打出 `tap: synth: ...`，
  含子串 `"tap: "`，与「按钮被点」的 `cc: tap: Volume` 撞车 ⇒ 做禁词校验的回归脚本会把
  合成触摸本身误判成「按钮被误触」（曾制造 9/23 假阳性）。禁词要写 `"cc: tap: "`（带完整 tag）。

- ⚠️ 钩子必须只做 `lv_async_call(...)` 转到 LVGL 线程：console RX 是独立 FreeRTOS 任务，
  直接改 LVGL 对象 / indev 驱动会跨线程出问题。
- 测完若被切进某个 app，写回空白 otadata 回启动器即可（见上）。
- 用途举例：证明「点按」没被滑动判别逻辑误伤（回归探针），以及横滑确被 LVGL 原生抑制（无需自己拦）。

  浮层会吃掉这一发点按，而且**菜单卡片比旧版矮了**（高度 222 → 166）⇒ 点按坐标 (180,180)

### 🔴 2026-09-30 补：长按已删（`'p'`/`'J'`/`'^'` 现在是**负面判据**）+ `'^'` 的滚动语义 + 空槽几何

**① 长按弹菜单这条入口整个删了 —— 调试键的判据方向要反过来读。**
用户报「主页左右移动时经常误触」，根因不是手滑：**LVGL 的长按是「无条件」派发的** ——
`driver->long_press_time` 写死 `LV_INDEV_DEF_LONG_PRESS_TIME` = **400ms**，**到点就派发
`LV_EVENT_LONG_PRESSED`、不看位移**；而慢速起手横滑在那 400ms 内位移往往还没到 `APP_CLICK_SLOP`(24px)
⇒ 横滑会**先蹦出一个操作菜单**（真机实测抓过两次：「底部上滑 75px」落成
`slot 0: long press -> app menu`；`'D'` = 底部 (180,336) 上滑 25px×3 帧 也被判成长按）。
现在 `home_long_press_cell()` 是**纯 no-op**，调试键 `'p'`（第 1 格长按 800ms）/ `'J'`（第 2 格）/
`'^'`（最后一格）**只该打出**：

```
cell N: long press -> ignored (app menu is tap-only since 2026-09-30)
cell N: CLICKED after long press -> swallowed
```
**零 `app_menu: menu:`**。多出任何菜单行都是回归。

🔴 **改这条代码时 `LV_EVENT_LONG_PRESSED` 的绑定必须保留、不能连绑定一起删** ——
长按松手时 LVGL **仍会补发一发 `CLICKED`**（`lv_indev.c` 里 `if(proc->long_pr_sent == 0)`
只夹住 `SHORT_CLICKED`，紧随的 `CLICKED` 不受约束）⇒ 删了绑定就等于「长按 ⇒ 走点按分支 ⇒
照样弹菜单」，**等于没删**。真正的失效靠 `home_long_press_cell()` 里保留的两句置位：
`s_app_long_pressed = true`（吞掉那发 CLICKED）+ `s_app_press_valid = false`。
—— 这条对任何「想删掉某个 LVGL 长按行为」的场合都成立。

**② `'^'` 现在是唯一能把「屏外末尾格」弄进视口的调试键。**
`'^'` 的语义在 2026-09-30 恢复字面（取 `s_cell_n - 1` = 最后一格），内部先 `lv_obj_scroll_to_view()`
再合成长按 ⇒ 日志会带上 `[scrolled into view]`，例：
`longpress cell 3 '' (kind=empty) live at (179,179) [scrolled into view]`。
⚠️ 为什么必须靠它：主页 4 格 582px > 屏 360px，而 `synth_touch_async()` 里**每次合成都先**
`lv_obj_scroll_to_x(s_row, 0, LV_ANIM_OFF)` **归零** ⇒ `'1'..'5'` **永远滚不过去**；
`'6'..'9'` 又全是 dx=+25 向右（见上）。截屏要拍屏外那几格时，这是唯一入口。

**③ 量「空槽内部圆与外圈描边的缝」：定式 + 正/反例对照。**
2026-09-30 口径：空槽（未安装的槽）**内部圆缩小、与外圈描边留 6px 缝**。
- 实现是**拆两个对象**（LVGL 的 `bg` **恒铺满对象**、没有「只让填充缩进去」的属性）：
  外层 `ic` 只留 `SLOT_BORDER_W`(2) 描边、内圆子对象 `ICON − 2×(BORDER + SLOT_INNER_GAP) = 116px`
  承担 40% 底色。⚠️ 缝**从描边内缘量起**（别写成 `ICON − 2×6` = 120，那样缝只剩 4px）。

### 2026-09-29 补：三个「验收脚本自己骗自己」的坑（都出在串口读取上）

**① 🔴 别用手势次数推断「现在在第几格」——用设备自己打的页码当日志判据。**
`','` 在真机上**并不总是推进一格**：实测同一轮里是 `1/5 → 2/5 → 回到 1/5 → 停住`。
用「发了 2 次就该在第 3 格」去截图，必然拿到错的格 —— 而图看起来「好像也对」，很难发现。
⇒ 每发一次就扫一遍 `launcher_ui: page: 'N/M'`，**只在页码正好是你要的那几页时才截图**。
（本轮要截第 3/4/5 格的三个推送项，就是靠这个循环拿到的；换成数手势次数时两张都截错了格。）
推而广之：判「有没有换格/换页」一律看**日志里那行页码变了没**，别靠时间、别靠次数。

**② 🔴 脚本里任何 `time.sleep` 都必须换成「边读边等」**（循环 `read()` 直到时间到）。
USB-Serial-JTAG 的 RX 环形缓冲很小，**脚本只要有几秒不读，设备日志就会被静默丢掉**。
本轮实测：`to_home()` 里有 3.4 秒纯 sleep（收浮层 + 连按 3 次上滑），那一窗口里
`'<'` 命令的两行日志整个消失，连带把 `':'` 的明细判据判成 ❌ —— **假阴性**。
反证：单独跑一个「只发 `':'`、不干别的」的探针，明细 **930 ms** 就回来了。
⇒ 症状是「设备明明打了、脚本里就是找不到」⇒ **先怀疑脚本没在读，别改固件**；
一个脚本里只留**一个 `recv` 出口**，所有等待都走它（这条与下面「所有 `read()` 都要进同一个日志缓冲」
是同一类错误的两副面孔）。

**③ 🔴 同一个 tty 只许**一个**进程 —— 两个脚本抢串口时上面的症状会全部复现（2026-09-29 又栽一次）**
macOS **不阻止**两个进程同时打开同一个 `/dev/cu.usbmodem*`（不像 esptool 会报
`Resource busy`）⇒ 两边各自只拿到**半截字节流**，谁都不完整。表现：
- 判据集体假阴性（"设备明明打了、脚本里找不到"）；
- 时序诡异：本轮 `step[1]` 找不到开机自证日志、`step[2]` 的 `'>'` 要 **60 秒**后才被"收到"；
- 设备被两边先后发的 `'R'` / `'Q'` / `'s'` 折腾得状态错乱。

🔴 **代价与教训**：为此白跑了**两轮**验收（各 10 分钟），还一度误判成"脚本的接收逻辑坏了" ——
加诊断口、手工分段复现（`SEQ='R:12,NONE:1,+:12'` 全对），全部对不上，因为**真正的原因在脚本外面**。
⇒ **排查串口疑难症状之前，先确认没有第二个脚本/监视器在跑**（`lsof /dev/cu.usbmodem*`，
或让脚本自己 `fcntl.flock` 拿一把非阻塞独占锁，拿不到就立刻退出并报出门牌号）。
先确认「只有一个读者」，再去怀疑接收逻辑。

## 端口会变（MAC 绑定）
`/dev/cu.usbmodem*` 的编号按设备 MAC 分配，同一台机器上换固件/换口都会变（见过 21101 / 21201 / 21301）。
每次都用 `ls /dev/cu.usbmodem*` 现查，别沿用上次的号。
⚠️ 设备刚复位/正被 esptool 占用时开串口会抛 `OSError: [Errno 6] Device not configured`。
这不是链路坏了：**关掉 esptool、等设备自己跑起来再重试**即可（2026-09-27 踩过一次）。

## 圆形屏幕的「圆内布局」怎么验：数值法，不靠肉眼（2026-09-27 补）

360×360 圆屏上，任何新 UI（尤其虚拟键盘这种满屏控件）都必须全部落在内切圆里，
判据是**外角点到圆心 (180,180) 的欧氏距离 < 180**。🔴 **不要靠「看图说看着没问题」**——
当前会话常常读不了图片文件（`Read` 返回不支持图像），那类结论没有证据。

正确的数值法（临时脚本 `/tmp/analyze_circle.py`）：

```python
# 逐像素亮阈值化，量到圆心的最大距离 + 圆外亮像素数
radius = max(sqrt((x-180)**2 + (y-180)**2) for 亮像素)
assert radius <= 180 and 圆外亮像素 == 0
```

实测 launcher 网络页 + 圆屏键盘页：**最大半径 158.9 px，圆外亮像素 0 个** ✓。

想看具体字符（例如键盘输入框里是不是真的打出 `22`），裁一小块出来转 ASCII：

```python
crop = im.crop((86, 68, 150, 95))          # 输入框区域
print('\n'.join('#' if px[x,y] > 140 else ' ' for y in ... for x in ...))
```

⚠️ 顺带一提：合成点按**别用 `'1'`**——它的坐标 (180,180) 正好落在键与键之间那几 px 的缝里，
永远打空且**截图毫无变化**；换一个落在键中心的坐标（如 `'A'` = (84,118)，数字行 `2` 键）。
判定同样以**日志**为准（`cc: kb: tap row=0 col=1 key='2'`），不以截图为准。


## 与「平台层验收」的配合（2026-09-19 补）

截屏只能证明**画面**，证明不了「状态有没有跨 app 传过去」——那类断言要靠**日志链**

这类断言建议单独写脚本跑，判据形如「同一组 vol/bri 在两边日志里逐字相等」。

常用串口调试键（**启动器与 app 不是同一套，别混**）：
- 启动器：`'v'` 音量滑块页 / `'w'` 亮度滑块页 / `'c'/'d'/'b'` CC 一级/数据/电量页 /
  `'l'` 启动 slot0 / `'p'`/`'J'` **长按第 1/第 2 个图标**（配 `'O'`/`'u'`/`'y'` = 应用菜单的

## 「app 烧了却跑的是启动器」：先查 otadata（2026-09-27 踩过）

现象：截图怎么截都同一屏；串口日志出现 `launcher_ui: synth ...`，或
`device_mode: running 'launcher' (subtype=0x00, factory), app='SDGOODS_LAUNCHER' -> MULTI`。
**不要**去查截屏链路。`write_flash 0x10000 <app>.bin` 只写 factory 槽，**改不了启动选择**：
只要 otadata 还指向 `ota_N`（里面存着旧启动器），复位后启动的仍是那个 ota 副本。

一步步核对 / 处置：

```bash
# ① 启动器到底在不在 factory？读 esp_app_desc（magic 0xABCD5432，project_name 在 +0x30）
esptool --chip esp32s3 -p <port> --after no_reset read_flash 0x10020 96 /tmp/fd.bin
# 解析：magic 对上 ⇒ project_name 就是当前 factory 身份（打印错则字节序/偏移不对）

# ② otadata 在 0x310000（本平台分区表，8KB）。全 0xFF ⇒ 回落 factory，即单应用直启
esptool --chip esp32s3 -p <port> erase_region 0x310000 0x2000      # 擦成全 0xFF
# 若 ① 显示 factory 里不是目标 app ⇒ 先 write_flash 0x10000 <app>.bin，再擦 otadata
```
擦完复位，日志应变成 `app='<你的工程名>' (not the launcher) -> SINGLE`。
启动选择判据（`device_mode`）比截图更可靠 —— 截到什么画面可以骗人，这条日志不会。

## 多步串口序列 + 应用上下文 CC 验证（2026-09-22 补）

### 2026-09-28 补：「按住型」调试键松手会**真的改变状态** ⇒ 脚本顺序本身就是判据

启动器里有一类调试键是 `sdgoods_tap_synth_hold(kx,ky,8000)` —— **按住 8 秒**（为了在按住期间
截到悬停态）。它松手时 LVGL 照样派发 CLICKED ⇒ **那一按键的功能会真的执行**。

实测翻车：`'$'`（按住**页切换键**）松手 ⇒ 键盘切到符号页；脚本紧接的 `--pre '.'`
（也是页切换）又把它切回字母页；再之后的 `'&'`（按住符号页**空格键**）就在字母页上找不到
`Space` 了。露馅方式：`v1100_kb_sym.jpg` 与 `v1100_hint_space.jpg` **SHA256 完全相同**
（两次截到的是同一帧），而串口给的是
`kb key center: token 'Space' not on this page (s_kb_n=40, sym=0)`。

**规矩：**
- **按住型键一律排在捕获序列的最后**；切片式的键（如 `'.'`）放在它前面。
- 判据先做**字节级自证**：两张本该不同的图若 SHA256 相同 ⇒ 别急着改代码，先怀疑 `--pre` 没生效
  （投递被覆盖、或前一个按住的松手把状态改了）。
- 一眼定位用 `--wait` 期内的串口日志（`not on this page` 那行会直接告诉你**当时是哪一页**：
  `s_kb_n` = 当前建出的键数，字母页 40 / 符号页 34 ⇒ 比 `sym` 标志位更可信）。

## 🔴 判据的**采样带**是「跟着界面位置走」的：改位置必须回头复核每一条（2026-10-01 补）

同一份判据，位置一改就可能**从"对"变成"错"**，而且两种错法都不报错：

| 形态 | 实例 |
|---|---|
| 旧采样带**圈进了新东西** ⇒ 假红 | 主页时钟从「顶部左侧」挪到「左边中间」（v2.0.25→v2.0.26）后，`bar_extent` 原本从 x=20 起扫状态条；旧版时钟第 1 行压在 **y 38..54** 那一带里，把日期文字也算成"图标" ⇒ 量出中心 145、判「图标组没居中」（功能是对的）。 |
| 旧采样带**圈不到东西了** ⇒ 假绿 | 位置一移走，"这块带里有字"就恒为假命题 —— 判据不再区分任何东西。 |

**规矩：**
- 判据脚本里的每条采样带都要写成**从几何常量推导**（`CLOCK_X ± 容差`），**不许写死**；
  改界面位置时**从源码常量同步过去**（本工程的做法：脚本里再写一条
  `assert CLOCK_Y + LINE_H == 180` 之类的"口径自证"，位置改错时脚本自己先炸）。
- 改完位置，除了跑"正例"，**必须重跑反例**（基线旧固件同带必须仍为黑 / 空白带必须仍为空），
  假绿只有反例抓得住。
- 🔴 **"两行都有字"这类判据抓不到"内容顺序写反"**。要验顺序，得用**形状量**：
  如「第 1 行墨迹比第 2 行窄」自证 `HH:MM` 在上、`MM-DD 周X` 在下。
- 采样带挪位后，**顺带把"位置本身"也变成判据**：如"第 2 行右沿 ≤ 居中图标格左沿 − 4px"，
  否则新位置撞到邻居也不会有任何判据红。

## 🔴 判据的「锚点」要设在**触发动作之前**，不能设在**后续导航之后**（2026-10-01 补）

「设备明明打了、切片里就是找不到」有**三种**成因，前两种是**没在读**和**别人也在读**，
第三种是：**锚点位置把这件事切到了窗口外面。**

本轮实例：关 Wi-Fi 的验收里，`clock: hidden (wifi=0 time=1)` 是在**点按开关那一拍**
（t=28017ms）就打出来的，而脚本把锚点 `mark()` 放在"点按 → 回主页"**之后** ⇒
`since(mark)` 整整错过它。同一份脚本的"日志要点"那节读的是**全量日志**，
于是症状最迷惑 —— **detail 里明明打印着那一行，判据却是 ❌**（同一轮里 5 条 ❌ 全是这个，
功能其实全对，白跑一轮）。

⇒ 规矩：
- 锚点取「**发那条触发指令之前**」，不是"操作做完、界面回去之后"；
- 越是**状态变化那拍同步打**的日志（`wifi up` / `xx: hidden` / `resync` / `sntp synced`）越容易踩；
- 配套写法：`pump()` **每轮复检 + 只在切片内搜**。只判"有没有读到新字节"的话，
  "等一件已经发生的事"会空转满超时再假红；而末尾若改用**全量** `text()` 兜一次，
  又会因该串在锚点之前就出现过而**假阳性** —— 两头都要堵。

## 🔴 判据的「测量目标」必须真的量出来，不能拿常量自己证自己（2026-10-01 补）

采样带要从常量推导（上一节），但**被测量的那个东西本身**必须**从像素上量**。
反例：口径是"时钟右沿到圆盘左沿 = 一个图标间距"，若写成
`abs(gap - ICON_GAP) <= 3` 但"圆盘左沿"直接代入常量 `114` ——
那是**拿定义验定义**，圆盘真挪了也照样绿。

本轮做法：写 `disc_left(img)` 真去图上找圆盘（某列在 y 176..191 内 ≥3 个非黑像素
⇒ 认为已进盘），量出来是 **114**、与设计值一致 ⇒ 判据才有信息量。
- ⚠️ 阈值要标定：盘内左侧可能有一段很暗的封面像素（实测 x 116..121 亮度 0~1），
  只看单行会把它当成盘外 ⇒ 用「多行计数」而不是「单点亮度」。
- 配一条**补刀判据**：两者之间那条空档带必须**全黑**（本轮 x 91..113 最大亮度 12），
  这样"量到的圆盘"与"字没顶上去"互相印证。
- 同类还有一个方向：**唯一口径应由常量推导、不要就地重算**（本轮 `CLOCK_X` 从
  `圆盘左沿 − 间距 − 字宽` 算出来、不写死 16）⇒ 几何改一处，脚本与固件才只有一处要同步。

## 🔴 「亮度比 / 梯度比」两态判据：**梯度比必须归一化**（2026-10-03 踩，差点误判）

验「压暗 / 蒙版 / 模糊」这类逐像素变换时，常用「同区域两态的**亮度比**」+「**梯度能量比**」
（相邻像素差均值）来判"到底做了什么"。**梯度比不能直接读，必须先除以亮度比。**

原因：压暗 = 给每像素乘 `f`（40% 黑 ⇒ `f=0.6`）⇒ **相邻像素差也按同一比例缩小**
⇒ 纯压暗的**原始**梯度比本来就 ≈ `f`（0.60），**不是 1.0**。

| 变换 | 亮度比 | 原始梯度比 | **归一化梯度比**（= 梯度比/亮度比） |
|---|---|---|---|
| 纯压暗 40% 黑 | 0.583 | 0.613 | **1.05** ⇒ 无模糊 ✅ |
| 高斯模糊 + 压暗 | 0.490 | 0.144 | **0.29** ⇒ 高频被抹平 ✅ |

⇒ 判据写成 `归一化梯度比 ≈ 1.0` ⇒ 纯压暗；`<< 1` ⇒ 有模糊。
⚠️ 本轮脚本第一版期望值写成 1.0，40% 黑打出 0.613 差点被读成"走了模糊"。

🔴 **绝对值不能跨"内容"比**：同一条判据在**壁纸被换掉之后**就失效了
（旧图基线 42.8、新图 88.6）。跨内容仍成立的硬判据是**「态 A == 态 B」**——
例如"普通态 == 极简态"（极简态从来没有蒙版），与底下是什么内容无关。

## 🔴 截图脚本的三个串口坑（2026-10-03 一轮里踩齐）

自己写验收脚本（不用 `screenshot_recv.py` 主流程）时，这三条必踩：

1. **`ser.read()` 会抛 `SerialException: device reports readiness to read but returned no data`**
   —— macOS 上偶发（另一个进程碰过同一 tty / USB 轮询抖动）。
   **必须 `try/except` 后继续等**，否则一个瞬时异常就把整轮验收打断
   （本轮第一版就这么丢掉了第一张图、后续像素判据整段没输出）。
2. **触发字符 `'s'` 要每 3 秒重发一次**（学 `screenshot_recv.run()` 里那句
   `if trigger and not asm.active and (time.time()-last_trig) > 5.0`）。
   只发一次时，**设备正忙 UI 线程那一拍会被整个吞掉** —— 表现就是"40s 内没收到完整图"。
3. **端口名会翻转** ⇒ 别写死，`sorted(glob.glob("/dev/cu.usbmodem*"))[0]` 自动选。

## 跑验收/分析脚本用哪个解释器

- **只要 pyserial**（纯收发/解析）：用装了 pyserial 的解释器即可（`python3 -c "import serial"` 自检）。
- **要 pyserial + numpy + PIL**（量化截图）：必须用**三个库都有**的解释器 ——
  **先自检再跑**，因为「有 pyserial」不等于「有 numpy」（曾拿只有 pyserial 的解释器跑量化脚本白跑一次）：
  ```bash
  python3 -c "import serial, numpy, PIL; print('ok')"
  ```
  ⚠️ 系统 `python3` 往往缺库 ⇒ 优先用 venv / IDF 自带的那份 python。
